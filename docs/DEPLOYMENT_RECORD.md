# Deployment record

What is actually running, where, and what went wrong getting there.

`DEPLOYMENT.md` is the guide — it explains how to deploy this stack from
scratch and why the hosts were chosen. This file is the record of the
deployment that exists today: real URLs, real settings, and the specific
problems that cost time, so they are not rediscovered later.

Deployed 17 September 2026. Every service is on a free tier and **no payment
method is attached to any of them**.

## What is running

| Layer | Service | Address |
|---|---|---|
| Frontend | Cloudflare Pages, project `nishanth-flux` | https://nishanth-flux.pages.dev |
| Backend | Render web service `flux-api` (Docker, free, Singapore) | https://flux-api-vono.onrender.com |

The backend and the database are both in Singapore on purpose: the API talks
to MySQL far more than it talks to users, so the chatty leg is the one worth
keeping short.

## 1. Database — TiDB Serverless

Cluster created in `ap-southeast-1` and seeded with `seed_mysql.py`: 30 tables,
182 transactions, 62 trades, and user id 1.

Connection settings that matter:

- `MYSQL_PORT=4000` (not 3306)
- `MYSQL_SSL=true`
- `MYSQL_SSL_CA` left **empty** — certifi's bundle is correct for TiDB, and
  pointing this at a file that does not exist on the Render image fails at boot

## 2. LLM — Groq

An API key from console.groq.com, set as `LLM_API_KEY`. `LLM_BASE_URL` points
at Groq's OpenAI-compatible endpoint, so no client code changes were needed.

`SENTIMENT_BACKEND=llm` in production: Layer 2c would otherwise load FinBERT,
and torch alone is 445 MB against a 512 MB instance.

## 3. Backend — Render

Created as a **Blueprint** from `render.yaml`, not by filling in dashboard
fields. Render reads the file, creates `flux-api`, and prompts only for the
values marked `sync: false`.

- Plan: **Free** (512 MB, 0.1 CPU). Confirm this after creation — the service
  page shows a `Free` badge next to `Docker`.
- Build time: 2m38s, because the image is torch-free.
- `AUTH_SECRET` is generated by Render, not supplied.
- `autoDeployTrigger: commit` — **every push to `main` redeploys the backend**,
  even a commit that only touches the frontend or docs.

Verified after deploy: `/health` returned `provider: openai`, all nine
scheduler jobs registered, chroma available, and ingestion already writing real
rows (15 crypto, 15 stocks, 901 ohlcv_history, 239 ohlcv).

## 5. Wiring the two together

Two files name the backend origin, and **both** must be set or the deployed
site cannot call the API:

- `js/flux-config.js` — `PRODUCTION_API`
- `pages/analysis.html` — the CSP `connect-src`

The CSP one is easy to miss. The browser blocks the API on that page
regardless of what `flux-config.js` resolves to unless the origin is listed
there as well. `dist/` is gitignored and rebuilt by Cloudflare, so only the two
source files are edited.

Then `CORS_ORIGINS` on Render is set to the Pages origin:

```
["https://nishanth-flux.pages.dev", "http://localhost:3000"]
```

It is parsed as JSON into a `list[str]`, so the brackets and double quotes are
required and a bare empty value fails at boot. Verified from outside: the
allowed origin receives `access-control-allow-origin`, an unknown origin does
not.

## 6. Keeping the instance warm

Render's free plan spins a service down after 15 minutes of inactivity, and the
next request then waits about 50 seconds. Three approaches were tried:

| Approach | Outcome |
|---|---|
| **UptimeRobot**, 5-minute HTTP check | **In use.** Reliable, and it reports genuine downtime as a bonus. |
| GitHub Actions cron (`.github/workflows/keep-warm.yml`) | Works, but drifts — a scheduled run went missing inside the first hour, and delays past two hours have happened on this repository. Left enabled as a backup. |
| Cloudflare Worker cron trigger (`keep-warm-worker/`) | **Never fired.** See below. |

Note for later: GitHub disables scheduled workflows in public repositories
after 60 days without commits, so the backup quietly stops if the project sits
untouched for two months.

## Problems hit, and what fixed them

### The Cloudflare Pages build never ran the frontend build

Cloudflare found `pyproject.toml` at the repository root and ran `pip install .`
before the configured build command. With `[project]` present but no package
list, setuptools attempted auto-discovery, found `js`, `css`, `pages`,
`assets`, `backend`, `ai_engine` and `mcp` side by side in a flat layout, and
refused to build. The build failed before `npm run build` was ever reached.

Fixed by declaring an empty package list in `pyproject.toml`:

```toml
[tool.setuptools]
packages = []
```

The application is never installed as a package — Docker and CI both install
from `backend/requirements*.txt` — so this costs nothing anywhere else.

### "Retry deployment" re-runs the old commit

The fix above sat unbuilt while two retries rebuilt the same previous commit.
Retry pins the commit that failed. Use **Create deployment**, or push.

### The Pages project silently disconnected from GitHub

A banner on the Deployments page said so, and pushes triggered no builds at
all. Reconnecting under Settings fixed it, but reconnecting does **not**
retroactively build anything — an empty commit was needed to give the restored
webhook something to fire on.

### Cloudflare's "Create application" defaults to the Workers flow

The Workers form has a *Deploy command* running `npx wrangler deploy` and no
*Build output directory* field. This repository has no wrangler config at its
root, and the build emits `dist/_headers`, which is Pages-specific — so the
Workers path was wrong twice over. The Pages form is the one with a **Build
output directory** field.

### Render emailed a "server failure" that was not one

Render's health check times out after 5 seconds; a free-tier cold start
legitimately takes about 50. The first idle period therefore produces an alert
for a service that is working correctly. Keep-warm is what stops it.

### Cloudflare cron triggers never executed

A Worker was written to replace the drifting GitHub cron. It never ran.

- `wrangler deploy` reported `schedule: */10 * * * *`, and the dashboard showed
  the trigger with a Next time that advanced correctly.
- Invocations stayed at zero across two separate workers, including a
  brand-new one with the simplest possible expression, `* * * * *`.
- The handler itself is provably fine: `wrangler dev` plus
  `curl http://localhost:8787/cdn-cgi/local/scheduled` logs the ping and a 200
  from Render.
- Documented propagation delays (15 minutes for the trigger, 30 for event
  display) had all elapsed. Cron triggers are available on the free plan — the
  limit is 5 per account.

No cause was found; it appears to be account- or platform-side. The worker
remains in `keep-warm-worker/` as a record, and UptimeRobot does the job.

### UptimeRobot reported the API as down while keeping it warm

UptimeRobot sends **HEAD** by default, and choosing the HTTP method is a paid
feature. FastAPI — unlike plain Starlette — does not register HEAD alongside
GET, so `/health` answered 405 to every check and the monitor showed the
service as down. The pings were still arriving and still keeping the instance
awake; only the reporting was wrong.

Fixed by accepting both verbs:

```python
@app.api_route("/health", methods=["GET", "HEAD"])
```

## Verifying a deployment

```bash
# Backend healthy, LLM wired, scheduler running
curl -s https://flux-api-vono.onrender.com/health

# Both verbs answer, so any uptime monitor works
curl -s -o /dev/null -w "%{http_code}\n" -I https://flux-api-vono.onrender.com/health

# CORS allows the deployed frontend
curl -s -D - -o /dev/null https://flux-api-vono.onrender.com/health \
  -H "Origin: https://nishanth-flux.pages.dev" | grep -i access-control

# ...and refuses anything else (expect no access-control header)
curl -s -D - -o /dev/null https://flux-api-vono.onrender.com/health \
  -H "Origin: https://example.com" | grep -i access-control

# Authenticated path
curl -s -X POST https://flux-api-vono.onrender.com/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"nishanth@flux.app","password":"FluxDemo@123"}'
```

`/health` should report `"provider": "openai"`, `"scheduler": {"running": true}`
and non-zero ingestion rows.

## Standing constraints

- **`flux-api` must remain the only service in the Render workspace.** The free
  plan gives 750 instance-hours per month and a month is 730. Keeping one
  service continuously awake fits with about 20 hours to spare; a second free
  service puts the pair over and suspends both for the rest of the month.
- **Do not lower `INGESTION_INTERVAL_MIN` below 30.** Nine scheduler jobs at the
  5-minute default exhaust NewsAPI's 100 requests per day within hours. Market
  data quota is the binding constraint, not compute, and the LLM now sits in
  that path too.
- **Render's disk is ephemeral.** SQLite ingestion history and the Chroma
  vector store reset on every deploy and every spin-down. Anything that must
  survive belongs in MySQL.
- **512 MB is a real limit.** The app boots at about 120 MB and reaches
  250-400 MB in use. If it runs out of memory, drop `chromadb` from
  `backend/requirements-slim.txt` first.
- **The demo password is public.** `FluxDemo@123` is in `backend/auth.py` and in
  the README, so anyone can sign in as user 1 and change that account's data.
  It is all synthetic seed data, which is the point of a demo — but nothing
  real should ever go behind that account.
